# IDI 资料管理：开发范围与验收

## 已确认的业务规则

- 以案件为归档单位。同一户可以同时存在多个案件；报案号为空时以项目、位置和案件内容区分。内部 ID 稳定，补上报案号不会另建案件。
- 短编号按项目简称、楼栋、房号和序号生成，工人将其填入水印。平台报修编号、保单号、保司报案号分开保存。
- 维修人员在自有水印相机填写编号、施工项目、施工区域、施工内容。当前由照片文件夹持续接收原件。
- 管理人员以检索、核对例外和提取资料为主。系统保留未归属、未知阶段和文件未下载等状态，不把缺失信息填成已完成。
- 照片按查勘、施工、验收等阶段组织，部位/工序与阶段分开。打卡用途区分楼栋、入户门；不同施工日期或到访记录分别检查。
- 一案可以包含多个维修部位，不能把主卧和客厅自动拆成两个案件。
- 保留原文件、内容哈希、来源、原文件名、水印时间、EXIF 时间、消息时间和接收时间。文件名中的时间不能当作拍摄或发送时间。
- 报送包记录不可变快照；再次报送或补件建立新版本。完工照片不能代替签字验收或保险公司回执。
- 户内位置与公共区域均可保存，楼层/房号使用文本。

## 界面

两个主看板：理赔受理、查勘维修。左侧共用项目、楼栋、案件导航；照片明细作为辅助工具，每张照片一行。首列为缩略图，其他列可选择；支持筛选、排序、分页、多选、查看大图、核对元数据和批量提取。

## 本轮实现

1. Windows 本地可运行系统：FastAPI、SQLite、独立原文件档案和 React 工作台。
2. 项目/案件的创建、编辑、搜索和归档状态；可空报案号、别名、维修部位与业务日期。
3. 文件/文件夹/ZIP 批量导入、台账 CSV/XLSX 预览与导入、导入批次结果和失败明细。
4. SHA-256 去重与原件保留；同一文件的多个来源不丢失；原件复制到档案后不依赖样例目录。
5. 本地 OCR、水印字段提取、候选案件匹配、结果核对和审计记录；不以识别失败替代人工结论。
6. 缺项核对、按日期/到访检查打卡；可配置保险公司资料要求。
7. 所选照片生成分类 ZIP、Excel 索引、Word 照片报告和 JSON 快照；报送版本、回执、补件记录。
8. 可配置文件收件目录、微信只读采集适配器和外部图片识别接口；持续任务状态、失败和重试。
9. 启停、备份、恢复工具、测试、文档与实际样例验收。

## 验收重点

- 用户样例 14 张照片的原文件 SHA-256 与归档一致，重复导入不增加重复照片。
- 同户两个案件保持独立；临时案件补报案号不更换 ID；长报案号文本不丢精度。
- 模糊匹配进入候选核对，识别结果不覆盖人工确认字段。
- 文件名时间与水印时间不混淆；缺施工打卡和查勘楼栋打卡能显示来源依据。
- ZIP/Excel/Word 内容、原图数量与所选范围一致；修改案件后旧报送快照不变化。
- 重启后数据、队列和档案保留；错误/坏文件不会把批次错误标为成功。
- 前端真实调用 API，并完成创建案件、导入、筛选、核对、导出和下载验证。
