# V2 案件工作台

两个主看板为“理赔受理”和“查勘维修”；项目、楼栋、案件共用左侧导航。照片、文件夹、报送、任务和设置放在“资料工具”中。

## 案件办理

理赔受理提供“待维保受理”“待保司复核”“待保司处理”“历史待核实”四种筛选；默认的“官网清单”保留官网该列表中的全部记录，包括已进入后续流程的案件。查勘维修按官网维修列表的成员展示，同一案件可以同时存在于两张清单中。小业主报案后，由施工 / 维保单位办理受理；受理结果为“现场查勘”时直接进入查勘维修。受理结果为“直接赔付”或“疑似非保险责任”时，才进入对应的保司复核分支。官网流程为“待处理”且当前处理人为保司的记录，列为“待保司处理”，不能作为维保待办。已关联官网的案件不能用本地按钮改进度。未关联的本地案件在“本地案件”中展示，可以在“办理记录”登记实际外部办理结果、时间及凭据说明，按受理、查勘、修复、验收、结算顺序办理；保司复核单列为受理结果分支，批准结果必须与此前提交的分支一致。

官网台账同步分别遍历理赔受理、查勘维修的未筛选完整列表，每页 40 条；检查总数、重复页和漏页。按官网记录 ID 关联本地案件，同时保存每张清单的成员和顺序。全部列表和案件核对成功后，事务内更新两张看板的清单；发生错误显示“部分完成”，保留上一次完整清单和同步时间。官网列表暂时不再出现的案件不会被删除。本地填写的案件内容、负责人、照片、草稿和报送记录保留。

“官网清单”总数不受本地项目、楼栋、搜索或进度筛选影响；“当前显示”给出筛选后的数量。本地样例不计入官网总数。官网维修清单中的案件不能仅因受理 `flowStatus=9` 而判为已结束：这是受理子流程结束，维修进度还需读取 `siteSurveyState`、`repairAcceptanceFlowStatus` 等维修字段。`repairAcceptanceFlowStatus=1/2/9` 分别表示验收、申请结算、维修流程结束；流程结束的记录若仍在官网清单中，也会显示在默认完整列表内。

对早于 2026-09-24、缺少受理结果且不在查勘维修清单中的记录，当前规则标记为“历史待核实”，完整保留并只读展示，不计入维保待办。该日期是既有历史数据核验形成的分界，不代表官网测试期；早于此日期但已有有效受理结果或维修清单归属的案件，仍按真实进度展示。新回读提供有效依据后恢复正常分类。其他无法识别的流程状态仍保留为同步异常，不猜测进度。

官网接口记录 ID、报修编号、保单号、保司报案编号分开保存。报修编号唯一定位业务案件；同一保单或报案号可以关联多个本地案件。短编号格式为 `项目简称-楼栋-房号-序号`，例如 `BYF-1-201-02`；有单元时增加 `U单元` 段。项目简称初始按拼音生成，可在项目设置中修改。保存时同步更新本项目已有案件短编号的简称部分；楼栋、单元、房号及序号尽量保留，目标编号已被其他案件使用（含历史编号）时顺延序号。每个曾用编号永久保留原案件归属，重复修改或改回简称不会断开旧水印关联。案件主键、官网编号、照片归属及历史报送快照不变。看板、快速导航和照片搜索均接受旧编号，案件详情可查看历史短编号。

## 文件夹和水印

在“照片文件夹”配置已有收图目录，启用后服务递归接收照片、视频及 PDF。需连续两次扫描确认文件大小与修改时间稳定至少 3 秒；读取前后再次检查文件状态。源文件保留，归档原件按 SHA-256 去重，相同文件的不同来源分别记录。文件夹不应位于工作台内部档案目录，也不能包含该档案目录。

本机已启用的收图目录是 `D:\Project\IDI\inbox`。把原图保存到这里，工作台会在服务运行时自动接收并进行本地 OCR。已有且唯一归属某案的重复原件会保留原案件归属，并补充本次收件来源。

工人在自己的水印相机填写以下四项，在案件详情点击“水印填写内容”即可复制：

```text
编号：BYF-1-201-02
施工项目：铂悦府
施工区域：1栋-201号
施工内容：查勘打卡
```

时间使用相机自带时间。施工内容按实际环节填写“查勘打卡”“XXX问题”“施工打卡”“XXX施工”“XXX完工”。对应看板五列：查勘打卡、查勘问题、施工打卡、施工、完工验收。PDF 不计为照片；编号或位置冲突的照片不计入有效数量。当前及历史短编号均采用精确匹配，不猜测 O/0 或 I/1；找不到或与位置冲突时进入人工确认。0.2.10 起，已识别为查勘或施工打卡的照片，会核对水印之外的清晰楼栋牌、入户门牌；独立号码与水印楼栋或房号精确一致且用途唯一时，自动区分楼栋和入户门，保存文字位置与置信度作为证据。仅水印写了地址、号码模糊、楼栋与房号同时出现或没有可靠文字位置时，仍由管理人员在照片详情确认。新草稿自动带入对应栏位；已有草稿通过“采用本环节照片建议”补入，不覆盖手动选材。

0.2.8 同时支持直接填写官网案件编号的水印：“小区”识别为项目名称，“工程名称”识别楼栋房号，“打卡内容”的“查勘打卡 / 查勘 / 维修打卡 / 维修 / 验收”分别进入上述五类。此时“施工内容”可以填写缺陷描述，分类以“打卡内容”为准。OCR 将日期与时间连在一起时仍能解析水印时间，不把日期误认作房号。

完整案件编号（示例：`ZLBH209901010000000001`）精确定位已同步的案件；同名小区的不同地块由该编号区分。0.2.9 起，编号唯一匹配时以案件编号为准：项目、楼栋、房号、短编号等差异仅在“识别建议”保留提示，不再标记为识别冲突，照片正常计入有效数量。未知案件编号或同时出现多个不同的完整案件编号时仍待核对；不猜测编号字符，不自动更改案件地址、办理状态或已人工确定的照片归属。没有完整案件编号时，旧短编号水印继续适用原规则。

两个看板的案件编号单元格上方为官网报修编号，下方为短编号；“报修日期”列放在编号之后。官网案件使用已保存列表 / 详情的 `reportDate`，本地案件使用已登记的报案日期；没有日期时显示“—”，不使用导入、创建或同步时间填补。查勘维修的日期跨官网、本地两行合并展示。

## 官网与本地照片对照（0.2.4）

查勘维修看板每案展示两行：上行“官网”来自最近保存的官网附件快照，下行“本地”来自已归档原件。案件编号、问题、进度和操作合并显示；点击本地数量打开该案、该分类的原件。官网数量不代表已经下载到本地，本地数量也不代表已经上传官网；不通过数量差推断缺失文件。

官网查勘打卡合并现场查勘的楼栋、入户打卡图片；查勘问题优先统计官网维修环节的缺陷照片汇总（含报案及查勘带入）；尚无维修环节时统计查勘缺陷照片，已有维修记录但汇总栏未读取时标为已确认的部分数量；施工打卡合并修复成果的楼栋、入户打卡图片；完工验收统计修复后照片。官网没有独立的“施工过程照片”栏，显示“—”。同一栏组按附件 ID（缺少时按文件地址）去重；维修环节的缺陷汇总已经包含查勘照片，不再与查勘栏叠加。视频和 PDF 不计入照片，所属栏位中的视频或其他附件另作小字提示。

确认空附件列表或确认尚无该阶段记录才显示 0。未读取、未关联分别明示；只读取部分栏位或存在未知文件类型时，显示“≥已确认数量”或“待核实”。官网行可悬停查看快照最近同步时间；读取看板本身不触发官网请求。两层表头整体固定，纵向滚动不会互相覆盖；窄屏通过表格内部横向滚动查看全部列。

## 平台和保司资料

案件详情按受理、现场查勘、修复成果、维修成果验收展示官网实际字段。只有当前办理环节可以填写业务信息、选择附件及保存草稿；进入下一环节后，前一环节仅供查看，尚未进入的环节不可提前办理。直接赔付、疑似非保险责任等分支等待保司复核时也不能修改受理内容；历史待核实、待保司处理均无可编辑表单；官网明确退回并回读后，才能重新受理。结算、结束及转入其他流程时，四个表单均只读。

已完成受理的案件，在理赔受理清单点击“查看”只展示受理记录；可通过“前往查勘维修”进入当前办理环节。查勘维修清单点击“处理”直接打开当前表单。例如案件当前处于修复成果环节时，受理、查勘信息与已有附件只读，修复成果可以准备，验收入口尚未开放。

0.2.11 的现场查勘表单提供“根据资料预填”：点击时按最新选材与当前填写重新计算，仅补空栏。实际查勘时间优先参考所选查勘打卡水印；多个日期不自动选定。缺陷原因仅参考官网已保存查勘内容或受理原因说明，缺少原因记录时保持空白；报修现象不能自动变成原因结论。分部工程、类型按明确问题文字匹配当前官网字典，多类别并存时提示人工选择；缺陷部位取已登记部位或原文用语。同案施工及完工照片的有效水印均在本次查勘同一天且时间顺序一致时，可建议“当天维修”及日期。人员选项、导入时间和完工照片数量不会成为人员、金额或验收状态的依据。每项建议显示来源并允许修改，已有草稿内容和附件保留，仍需保存本地草稿。

历史官网表单使用最近回读的已保存字段和附件；此前本地草稿仍保留用于追溯，不覆盖历史官网内容。后端同样检查阶段，旧页面或直接接口请求不能保存旧阶段、生成新的阶段资料包或重提过期审核。当前环节默认按照片阶段和用途建议选材；修改过的草稿不会被重新同步覆盖。日期填写实际办理时间，不使用导入、上传时间填补。业主验收 PDF 和补充 PDF 在验收环节由管理人员选择。

保司资料与广州平台共用原件，按独立模板检查。模板支持五类照片、最低数量、具体部位、工序关键字和每次到访检查。可以生成包含原件、索引、报告、快照和缺项说明的资料包；生成文件不会改变案件业务进度。

“预提交审核”保存当前案件、全部字段、选材原件和版本指纹。审核后字段、文件归属或官网资料变化会使审核失效。0.2.12 区分三种操作：“保存本地核对记录”只保留本机记录；“保存到官网（不提交）”上传附件并保存草稿，现场查勘和修复成果保持当前环节；“确认并提交”才正式提交并回读业务进度。受理和验收接口没有官网草稿动作，因此不显示官网保存按钮。

保存或提交前会重新读取官网，并再次验证原件。上传进度、官网拒绝原因及待核对项目在审核页显示。上传中断或官网明确拒绝时，可修正后重试并复用本批已取得的上传回执；业务请求结果未知时先回读，阻止重复提交。官网成功响应后如果回读暂时失败，保留成功回执，不把它误判为可重新执行。官网保存回读一致后，已上传原件转为“官网已有”，本地原件、填写内容和审核快照继续保留；随后正式提交不会再次上传这些文件。

通过 `start.cmd` 或 `scripts/start.ps1` 启动时启用人工核对后的官网写入；`scripts/start.ps1 -ReadOnly` 可只读运行。直接运行 Python 服务仍以 `IDI_PLATFORM_WRITE=0` 为默认值，显式设为 `1` 才开启写入。切换模式需停止后重新启动。密码、令牌只在服务内存中保存，重启后重新连接。

## 保存与恢复

数据库为第 7 版；0.2.6 新增短编号历史索引，并在同一迁移事务中补齐旧版本已修改简称的案件，保留旧编号及逐案审计记录。重复启动不重复改号。0.2.3 增加“历史待核实”和“待保司处理”两个状态，并修正受理分支。迁移在事务内扩展状态列约束，不重建案件主键或关联档案；触发已有资料目录索引刷新。升级前保留数据库/原件备份和源码快照。原件、来源、人工修改、办理事件、审核快照和报送版本可追溯。`data/项目资料/` 是可恢复的浏览副本，人工修改造成的副本冲突会报告而不会覆盖；原件仍在内容寻址档案中。

官网同步使用独立网络任务线程，本地导入、OCR、导出继续执行。服务关闭期间不会主动收图；重新启动后扫描文件夹补收已有新文件。未启用微信采集或外部视觉服务。
